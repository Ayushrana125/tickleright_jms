## Project overview

Build a complete, working frontend prototype of a **Journey Management System (JMS)** for Tickle Right, a right-brain education company for children. This is an internal marketing operations tool — the audience for this demo is the marketing team, not engineers. The goal is for them to see and click through the actual concept (not a slide deck) before real backend work begins.

This is a prototype: no real backend, no real database, no real WhatsApp/Email/Call integration. Use mock/seed data and local state (React state + localStorage for persistence between reloads) to simulate everything. Every screen should feel real and functional to click through, not static.

## Build order

Build in this order, and get each stage working end-to-end before moving to the next — don't scaffold all four modules shallowly at once:

1. **Journey module first** — this is the centerpiece and the hardest part (the React Flow canvas, node types, branching, simulation, action log). Get this fully working, including the pre-seeded example journey below, before touching the other modules.
2. Then Templates (needed for the Journey module to reference real content)
3. Then Audience (needed for the Journey module's inclusion/exclusion pickers)
4. Then Analytics last, since it depends on data generated by the other three

## Tech stack

- React (JSX, not TypeScript)
- Vite
- Tailwind CSS
- React Router for navigation between modules
- No backend — mock data lives in a local JSON/JS data file, state managed via React (Context or Zustand is fine), persisted to localStorage so a demo doesn't reset on refresh

## Brand identity

Pull the visual identity from Tickle Right's actual site (tickleright.com) and existing brand assets:
- Primary brand color: warm coral/pink (Tickle Right's signature color, used in their logo and site — sample around `#E85C7B` / `#F06292` range, refine by eye to match their actual logo pink)
- Supporting palette from their site's content blocks: soft sky blue (`#A8D8E8` range) and warm orange (`#F5A94E` range)
- Friendly, rounded, playful character-driven visual style (their site uses illustrated animal mascots — crab, panda, monkey) — the JMS tool itself should NOT use mascots (it's an internal ops tool, not the parent-facing site), but should carry the same warmth: rounded corners, soft shadows, friendly sans-serif typography, generous whitespace
- Typography: one clean, rounded sans-serif for both headings and body (e.g. Nunito, Quicksand, or similar warm-but-professional family), with a clear type scale — do not default to a generic SaaS/dashboard font
- This is an internal tool for a marketing team, not a childrens' product — keep it warm and approachable, but prioritize clarity and information density in the Journey builder and Analytics screens over playfulness. Playfulness lives in the color/type choices, not in decoration.
- Avoid generic AI-generated dashboard tells: no identical rounded cards with the same grey shadow on everything, no tracked-out ALL-CAPS eyebrow labels, no arrows appended to every button, no gradient washes as decoration for their own sake.

## Information architecture

Four modules, accessible via a persistent left sidebar or top nav:

1. **Audience**
2. **Templates**
3. **Journey**
4. **Analytics**

---

## Module 1: Audience

Purpose: segment and save member data for use in journeys.

- A list view of saved audience segments (e.g. "All Members," "Graduated," "Age 4-6," "Mumbai Centre," "Discontinued — Last 30 Days")
- A segment builder: filter members by fields such as age group, city/centre, lifecycle stage (Lead / Active Member / Discontinued / Graduated / Franchise Interest), joining cohort, trainer, counsellor
- Each segment shows a live member count based on mock data
- Ability to save a segment with a name for reuse inside Journey audience inclusion
- A separate **Exclusion list** capability: ability to search and add specific Member IDs to a global or journey-specific exclusion list, with a reason/note field (e.g. "complaint raised," "requested opt-out") — this is the mechanism for manually pulling one specific person out of any journey regardless of segment membership
- Mock dataset: generate ~150-300 fake member records (name, age, city, lifecycle stage, joining date, trainer, counsellor) to make filtering feel real

## Module 2: Templates

Purpose: create the actual communication content used inside journeys. Internally call this module "Templates" in the UI, but the underlying concept is a single reusable unit = **one message on one channel**.

- A list of saved templates, each showing: name, channel icon (WhatsApp / Email / Call / Gift), a preview of the content, last edited date
- A template editor:
  - Channel selector: WhatsApp, Email, Call, Gift
  - Content type: Text only, or Image + Text
  - Text field with support for simple variable placeholders (e.g. `{{child_name}}`, `{{parent_name}}`, `{{centre_name}}`)
  - Image upload/preview (can be a placeholder image picker for the prototype)
  - For Call and Gift channels: instead of message content, show a "Call Script / Instructions" text field and a "Notes for stakeholder" field, since these are human-executed steps, not automated sends
- Templates are the building blocks selected inside Journey steps

## Module 3: Journey — the centerpiece

Purpose: a visual journey builder, similar in interaction model to n8n or Zapier's flow builder, but oriented **vertically by default** rather than horizontally. Steps stack downward, but nodes are freely draggable anywhere on the canvas — the layout is not forced into a straight line, it just needs each node connected to its logical previous step with a visible connector line.

### Journey list view
- List of all journeys with: name, status (Draft / Active / Paused), type/tag (e.g. Member Journey, Cold Lead Journey, Discontinued Journey, Graduate Journey, Franchise Investor Lead Journey — these are just example tags, not fixed system categories; users can create their own journey types), member count currently in journey, last modified

### Journey builder canvas
- Free-form drag-and-drop canvas (use `reactflow` / `@xyflow/react` library — it's the standard tool for exactly this kind of node-based builder and will save significant build time vs. hand-rolling one)
- A **Start node** representing the trigger:
  - Trigger type: Event-based (e.g. "Registration," "Renewal Due," "Payment Failed" — a dropdown of mock business events) OR Time-based (recurring on a schedule)
  - Audience: pick an inclusion segment (from Module 1) and optionally an exclusion list/specific Member IDs
- **Step nodes**, each connected to a previous node, each configurable with:
  - Timing: offset from trigger event, expressed as a number + unit (Days / Weeks / Months) — e.g. "M+5" reads as "5 days after trigger"
  - Which Template (from Module 2) fires at this step
  - A toggle: "Avoid Sundays" (per-journey or per-step option — if the calculated send date lands on a Sunday, push to next valid day)
  - A toggle/flag: "Check festival calendar" and "Check content calendar" before sending (for the prototype, this can just be a checkbox with a tooltip explaining the eligibility check — doesn't need real calendar integration)
- **Branch/Route nodes**: allow a journey to split into multiple paths (e.g. after a "Day 367" milestone node, branch into a "Discontinued" path and a "Graduated" path), each continuing with its own sequence of step nodes, and optionally converging back into a shared downstream node
- **Reminder/Human-action nodes**: for Call or Gift template steps, instead of "sent," these generate a task. Show this visually distinct from automated steps (different node color/icon)
- A right-side panel that opens when a node is selected, showing all its configurable fields (this keeps the canvas clean and matches the standard n8n/Zapier interaction pattern)
- Save / Publish / Pause controls for the whole journey

### Simulation mode
- A "Simulate" button on any journey that runs a compressed-time preview: 1 real day = 1 minute, 1 week = 7 minutes, 1 month = 30 minutes (make this configurable/obvious in the UI, e.g. a speed selector)
- While simulating, show a live timeline/log panel: which mock members are hitting which step, when, and what would be sent — this lets a marketing person "watch" a 367-day journey play out in a few minutes without needing real time to pass
- A pause/stop control for the simulation

### Action log (for Call/Gift human steps)
- A separate "My Tasks" or "Action Queue" view listing all pending human-action steps assigned to the current stakeholder/counsellor (mock a logged-in user)
- Each task: member name, journey, step, due context, and an end-of-day comment field where the stakeholder marks the outcome (e.g. "Called — spoke to parent," "Not reached," "Gift delivered") — this becomes the completion record for that step

### Pre-seeded example journey: "Member Journey"

Seed the app with one fully built-out example journey already on the canvas when the app loads, so the marketing team sees a real, populated journey immediately rather than a blank canvas. Build it exactly as follows:

- **Journey name:** "Member Journey"
- **Trigger (Start node):** Event-based — "Member Joined the Program" (call the trigger reference `M` in the UI, e.g. step labels show "M+5")
- **Main sequence** (each a Step node, connected in order, each referencing a real seeded Template of the matching channel):
  1. Day 1 (M+1) — WhatsApp — "Welcome & Onboarding" message
  2. Day 5 (M+5) — WhatsApp — "Trainer Introduction" message
  3. Day 9 (M+9) — Call — a Reminder/human-action node — "Personal check-in call" with a stakeholder notes field
  4. Day 17 (M+17) — WhatsApp — a progress/learning resource message
  5. Day 30 (M+30) — Email — "Parent Check-in" email
  6. Day 100 (M+100) — Gift — a Reminder/human-action node — "Send a small gift (e.g. via Zepto)" with delivery confirmation notes
  7. Day 367 (M+367) — WhatsApp — "Annual Connection" message
- **Branch at Day 367** — a Route/Branch node splits into two paths:
  - **Discontinued path:** if the member's status changes to Discontinued at any point, branch to a shorter sequence — D+1 (pause promotional communication), D+3 (personal check-in), D+7 (understand the reason), D+30+ (recovery or gentle community connection) — each a Step or Reminder node as appropriate
  - **Graduated path:** if the member graduates, branch to — G+0 (graduation recognition message), G+7 (alumni learning resources), G+30 (trainer and community connection), G+90+ (events and referrals)
  - Both branches **converge into a shared end node**: "Tickle Right Community" — representing ongoing lifelong engagement (alumni meetups, community events, referrals/advocacy)
- Every node in this seeded journey should be fully configured (real template reference, real timing, Avoid Sundays toggle set, etc.) — not placeholder/empty nodes — so clicking into any node shows a complete, realistic example of how a journey is built.
- This seeded journey should also have a handful of mock members already "in progress" at different steps, so the Analytics module and the Action Queue have real data to show against it from the start, and so the Simulation mode has something meaningful to play through immediately.

## Module 4: Analytics — Lifecycle Control Tower

Purpose: management-level visibility into where families are and how journeys are performing.

- A summary dashboard: current member count by lifecycle stage (Lead, Active, Discontinued, Graduated, Franchise Interest), shown as a simple funnel or stage-based visualization
- Per-journey performance: entries, completions, drop-off rate, average time-in-journey, step-by-step conversion (how many people reached each step vs. the one before)
- Filters: centre, city, lead source, campaign, journey, joining cohort, channel
- A simple alert indicator: highlight (visually, e.g. a red badge) when a journey's completion or transition rate falls materially below a mock "baseline" — doesn't need real alerting logic, just a threshold comparison against mock historical data
- Use a charting library (Recharts is a sensible default) for any bar/line/funnel visualizations

## Data model to seed (mock data)

Set up these entities in the mock data layer so every module has real, cross-referenced data to work with rather than isolated fake data per screen:

- **Member**: id, name, child name, age, city/centre, lifecycle stage, joining date, trainer, counsellor, phone, email
- **Segment**: id, name, filter criteria, resulting member count
- **Template**: id, name, channel, content type, content/script, variables used
- **Journey**: id, name, status, trigger type/config, nodes (with positions for the canvas), edges/connections, tag
- **JourneyMember**: which members are currently in which journey, at which step, since when (drives both the canvas simulation and the analytics)
- **ActionTask**: linked to a JourneyMember + step, assigned stakeholder, status, comment

## What "complete working prototype" means here

Every module should be genuinely interactive, not a static mockup:
- Creating/editing a segment, template, or journey should actually persist (to localStorage) and show up in list views
- The Journey canvas should actually let you drag nodes, connect them, and configure each one
- Simulation should actually animate/progress in real (compressed) time and show believable output
- Analytics numbers should be computed from the actual mock JourneyMember data, not hardcoded

## Deliverable

A single working Vite + React + Tailwind app with the four modules above, seeded with realistic mock data, that a non-technical marketing person at Tickle Right can open and click through end-to-end to understand: how a segment is built, how a message template is created, how a journey is visually assembled with branching and human-action steps, how simulation lets them preview it fast, and what management would see in Analytics.
